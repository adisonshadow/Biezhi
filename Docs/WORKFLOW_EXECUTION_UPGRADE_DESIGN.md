# 工作流执行系统升级设计方案

## 1. 概述

### 1.1 设计目标

本文档描述工作流执行系统的升级方案，旨在支持更灵活的执行模式，包括：

- **一键执行工作流**：从头开始完整执行整个工作流
- **单节点执行**：仅执行选中的单个节点
- **部分执行**：从指定节点开始，执行该节点及其后续所有节点

同时，系统需要建立完善的数据版本管理和状态管理机制，确保执行数据的完整性和可追溯性。

### 1.2 核心需求

1. **执行模式多样性**：支持三种不同的执行模式，满足不同的调试和运行需求
2. **数据版本管理**：每次完整执行工作流时创建新的数据版本，部分执行时复用已有版本
3. **状态管理**：为每个节点维护独立的执行状态（待执行、执行中、成功、失败）
4. **内存数据存储**：在内存中维护所有节点的执行结果，支持快速访问和查询
5. **数据依赖追踪**：能够准确识别节点间的数据依赖关系，确保数据正确传递

## 2. 核心概念

### 2.1 执行会话（Execution Session）

执行会话是工作流执行的基本单位，代表一次完整的或部分的执行过程。每个执行会话包含：

- **会话ID**：唯一标识符
- **工作流ID**：关联的工作流
- **执行模式**：完整执行、单节点执行、部分执行
- **起始节点**：执行开始的节点（完整执行时为null）
- **数据版本号**：当前会话使用的数据版本
- **创建时间**：会话创建时间戳
- **状态**：会话整体状态（运行中、已完成、已失败、已取消）

### 2.2 数据版本（Data Version）

数据版本用于区分不同执行周期产生的数据。关键特性：

- **版本号**：自增的整数，每次完整执行工作流时递增
- **版本数据**：存储该版本下所有节点的执行结果
- **版本状态**：版本的整体状态（活跃、已归档）
- **版本时间戳**：版本创建时间

**版本创建规则**：
- 一键执行工作流时，创建新的数据版本
- 单节点执行或部分执行时，使用当前最新的数据版本（不创建新版本）

### 2.3 节点执行状态（Node Execution Status）

每个节点在执行会话中都有独立的状态：

- **PENDING**：待执行，节点尚未开始执行
- **RUNNING**：执行中，节点正在执行
- **SUCCESS**：执行成功，节点执行完成且结果有效
- **FAILED**：执行失败，节点执行过程中出现错误
- **SKIPPED**：已跳过，节点因前置条件不满足而被跳过
- **CANCELLED**：已取消，节点执行被用户或系统取消

### 2.4 内存数据存储（In-Memory Data Store）

内存数据存储是系统的核心组件，负责：

- **数据存储**：按版本和节点ID组织存储执行结果
- **数据查询**：提供快速的数据查询接口
- **数据版本管理**：维护版本间的数据关系
- **数据清理**：定期清理过期或不再使用的数据

**数据结构**：
- 顶层按工作流ID组织
- 第二层按数据版本号组织
- 第三层按节点ID组织
- 每个节点数据包含：执行结果、执行状态、执行时间、错误信息等

## 3. 执行模式详解

### 3.1 模式一：一键执行工作流（Full Execution）

**触发条件**：用户点击"执行工作流"按钮，未选中任何节点

**执行流程**：
1. 创建新的执行会话
2. 创建新的数据版本（版本号自增）
3. 获取工作流的拓扑排序执行顺序
4. 按顺序执行所有节点：
   - 对于入口节点，使用用户提供的输入数据或默认数据
   - 对于非入口节点，从上游节点的输出获取输入数据
   - 执行节点并将结果存储到当前数据版本
5. 更新节点状态为成功或失败
6. 完成执行会话

**数据版本**：创建新版本，版本号 = 当前最大版本号 + 1

**状态管理**：所有节点状态从PENDING开始，逐步更新为RUNNING、SUCCESS或FAILED

### 3.2 模式二：单节点执行（Single Node Execution）

**触发条件**：用户选中单个节点，点击"执行节点"按钮

**执行流程**：
1. 创建新的执行会话（执行模式标记为"单节点"）
2. 获取当前最新的数据版本（不创建新版本）
3. 检查选中节点的前置依赖：
   - 如果前置节点在当前版本中已有成功结果，使用该结果作为输入
   - 如果前置节点在当前版本中没有成功结果，尝试从更早的版本获取
   - 如果所有版本都没有前置节点的成功结果，执行失败
4. 执行选中的节点：
   - 从内存数据存储获取前置节点的输出数据
   - 执行节点并将结果存储到当前数据版本（覆盖该节点在该版本中的旧数据）
5. 更新节点状态
6. 完成执行会话

**数据版本**：使用当前最新版本，不创建新版本

**状态管理**：只更新选中节点的状态，其他节点状态保持不变

**注意事项**：
- 如果前置节点数据不存在，需要提示用户先执行前置节点
- 执行结果会覆盖该节点在当前版本中的旧数据
- 不会影响其他节点的数据

### 3.3 模式三：部分执行（Partial Execution）

**触发条件**：用户选中一个或多个节点，点击"从选中节点执行"按钮

**执行流程**：
1. 创建新的执行会话（执行模式标记为"部分执行"）
2. 获取当前最新的数据版本（不创建新版本）
3. 确定执行范围：
   - 从选中的节点开始
   - 通过图的遍历，找到所有后续节点（包括选中节点本身）
   - 构建部分执行的节点列表
4. 对执行范围内的节点进行拓扑排序（仅考虑执行范围内的节点连接关系）
5. 按顺序执行节点：
   - 对于执行范围内的入口节点（在执行范围内没有前置节点），从内存数据存储获取前置节点的输出（这些前置节点可能不在执行范围内）
   - 对于执行范围内的非入口节点，从内存数据存储获取前置节点的输出
   - 执行节点并将结果存储到当前数据版本
6. 更新所有执行节点的状态
7. 完成执行会话

**数据版本**：使用当前最新版本，不创建新版本

**状态管理**：更新执行范围内所有节点的状态

**注意事项**：
- 执行范围内的节点可能依赖执行范围外的节点，需要确保这些依赖节点的数据在当前版本中可用
- 如果依赖节点数据不存在，需要提示用户先执行依赖节点或执行完整工作流
- 执行结果会覆盖执行范围内节点在当前版本中的旧数据
- 不会影响执行范围外节点的数据

## 4. 数据版本管理机制

### 4.1 版本创建策略

**新版本创建时机**：
- 用户执行"一键执行工作流"操作时
- 系统检测到工作流配置发生重大变更时（可选）

**版本复用策略**：
- 单节点执行和部分执行时，始终使用当前最新版本
- 如果最新版本不存在，创建初始版本（版本号为1）

### 4.2 版本数据组织

**数据结构**：
- 每个版本维护一个节点数据映射表
- 映射表的键为节点ID，值为节点执行结果
- 节点执行结果包含：
  - 输出数据（按输出端口组织）
  - 执行状态
  - 执行时间戳
  - 错误信息（如果执行失败）
  - 执行元数据（如执行时长、资源使用情况等）

### 4.3 版本数据访问

**数据读取规则**：
1. 优先从当前版本读取节点数据
2. 如果当前版本中节点数据不存在或状态为失败，尝试从更早的版本读取
3. 如果所有版本都没有该节点的成功数据，返回数据不存在

**数据写入规则**：
1. 单节点执行和部分执行时，只更新当前版本中相关节点的数据
2. 完整执行时，在新版本中写入所有节点的数据
3. 数据写入是原子操作，确保数据一致性

### 4.4 版本清理策略

**清理时机**：
- 系统启动时清理过期的执行会话数据
- 定期清理不再使用的数据版本（保留最近N个版本）
- 用户手动清理指定版本

**清理规则**：
- 保留最近10个数据版本（可配置）
- 保留所有活跃执行会话关联的版本
- 清理时只删除数据，保留版本元数据（用于审计）

## 5. 状态管理机制

### 5.1 状态层次结构

**三层状态管理**：

1. **会话级状态**：整个执行会话的状态
   - RUNNING：执行中
   - COMPLETED：已完成
   - FAILED：执行失败
   - CANCELLED：已取消

2. **版本级状态**：数据版本的整体状态
   - ACTIVE：活跃版本，正在被使用
   - ARCHIVED：已归档，不再被使用但保留数据
   - DELETED：已删除，数据已清理

3. **节点级状态**：单个节点在执行会话中的状态
   - PENDING、RUNNING、SUCCESS、FAILED、SKIPPED、CANCELLED

### 5.2 状态转换规则

**节点状态转换**：
- PENDING → RUNNING：节点开始执行
- RUNNING → SUCCESS：节点执行成功
- RUNNING → FAILED：节点执行失败
- RUNNING → CANCELLED：节点执行被取消
- 任何状态 → PENDING：节点被重置（新版本创建时）

**会话状态转换**：
- 创建时：状态为RUNNING
- RUNNING → COMPLETED：所有需要执行的节点都完成（成功或失败）
- RUNNING → FAILED：关键节点执行失败导致整个会话失败
- RUNNING → CANCELLED：用户或系统取消执行

### 5.3 状态持久化

**持久化策略**：
- 节点状态实时更新到内存数据存储
- 定期将状态快照持久化到数据库（用于恢复和审计）
- 执行会话结束时，将最终状态持久化到数据库

**状态恢复**：
- 系统重启时，从数据库恢复最近的执行会话状态
- 恢复时重建内存数据存储（仅恢复最近N个版本的数据）

## 6. 内存数据存储设计

### 6.1 存储结构

**多级映射结构**：
- 第一级：工作流ID → 工作流数据容器
- 第二级：数据版本号 → 版本数据容器
- 第三级：节点ID → 节点执行数据

**节点执行数据结构**：
- outputData：节点的输出数据（按端口组织）
- status：节点执行状态
- executionTime：执行时间戳
- duration：执行时长（毫秒）
- error：错误信息（如果执行失败）
- metadata：执行元数据（资源使用、日志等）

### 6.2 数据访问接口

**查询接口**：
- 根据工作流ID、版本号、节点ID查询节点数据
- 根据工作流ID、版本号查询版本中所有节点数据
- 根据工作流ID查询所有版本列表
- 根据工作流ID查询最新版本号

**更新接口**：
- 更新节点执行数据（原子操作）
- 批量更新多个节点数据
- 创建新版本
- 删除指定版本

### 6.3 数据一致性保证

**并发控制**：
- 使用读写锁保护数据访问
- 节点数据更新时加写锁
- 节点数据读取时加读锁

**事务性**：
- 节点执行结果更新是原子操作
- 版本创建是原子操作
- 支持批量更新的原子性

### 6.4 内存管理

**内存限制**：
- 每个工作流最多保留N个版本（默认10，可配置）
- 每个版本最多保留M个节点的数据（默认1000，可配置）
- 系统总内存使用不超过阈值（可配置）

**内存清理**：
- 自动清理最旧的版本数据
- 定期清理不再使用的节点数据
- 支持手动触发清理操作

## 7. 执行流程详细设计

### 7.1 完整执行流程

**阶段一：准备阶段**
1. 验证工作流配置完整性
2. 获取工作流拓扑排序结果
3. 创建执行会话
4. 创建新数据版本
5. 初始化所有节点状态为PENDING

**阶段二：执行阶段**
1. 按拓扑顺序遍历节点
2. 对于每个节点：
   - 检查前置依赖节点的状态
   - 如果前置节点未成功，跳过当前节点（标记为SKIPPED）或终止执行
   - 从内存数据存储获取前置节点的输出数据
   - 构建节点输入数据（包括用户配置和前置节点输出）
   - 更新节点状态为RUNNING
   - 调用节点执行器执行节点
   - 将执行结果存储到内存数据存储
   - 更新节点状态为SUCCESS或FAILED
3. 如果关键节点失败，终止整个执行

**阶段三：完成阶段**
1. 收集所有节点的执行结果
2. 更新执行会话状态为COMPLETED或FAILED
3. 持久化执行结果到数据库
4. 通知前端执行完成

### 7.2 单节点执行流程

**阶段一：准备阶段**
1. 验证选中节点存在
2. 创建执行会话（模式：单节点）
3. 获取最新数据版本
4. 检查前置依赖节点数据可用性

**阶段二：执行阶段**
1. 从内存数据存储获取前置节点输出数据
2. 如果前置数据不可用，返回错误提示
3. 构建节点输入数据
4. 更新节点状态为RUNNING
5. 执行节点
6. 将结果存储到当前版本（覆盖旧数据）
7. 更新节点状态

**阶段三：完成阶段**
1. 更新执行会话状态
2. 通知前端执行完成

### 7.3 部分执行流程

**阶段一：准备阶段**
1. 验证选中节点存在
2. 创建执行会话（模式：部分执行）
3. 获取最新数据版本
4. 确定执行范围：
   - 从选中节点开始
   - 通过图的深度优先或广度优先遍历找到所有后续节点
   - 构建执行节点集合
5. 对执行范围内的节点进行拓扑排序
6. 检查执行范围外的前置依赖节点数据可用性

**阶段二：执行阶段**
1. 按拓扑顺序执行执行范围内的节点
2. 对于每个节点：
   - 如果前置节点在执行范围内，从当前执行结果获取数据
   - 如果前置节点不在执行范围内，从内存数据存储获取数据
   - 执行节点并存储结果
3. 更新所有执行节点的状态

**阶段三：完成阶段**
1. 更新执行会话状态
2. 通知前端执行完成

## 8. 依赖关系处理

### 8.1 依赖识别

**依赖类型**：
- **直接依赖**：通过连接关系直接连接的节点
- **间接依赖**：通过多个连接关系间接连接的节点
- **数据依赖**：节点需要前置节点的输出数据
- **配置依赖**：节点配置中引用了其他节点的输出（可选功能）

### 8.2 依赖检查

**检查时机**：
- 单节点执行前：检查所有前置依赖节点数据是否可用
- 部分执行前：检查执行范围外的前置依赖节点数据是否可用
- 完整执行时：按拓扑顺序自然满足依赖关系

**检查规则**：
1. 遍历节点的所有输入端口
2. 对于每个输入端口，查找连接的源节点
3. 检查源节点在当前版本中是否有成功的数据
4. 如果数据不可用，尝试从更早版本获取
5. 如果所有版本都没有数据，标记为依赖不满足

### 8.3 依赖错误处理

**错误类型**：
- **前置节点未执行**：前置节点在当前版本中没有执行记录
- **前置节点执行失败**：前置节点执行失败，数据不可用
- **数据版本不匹配**：前置节点数据来自不同版本，可能存在不一致

**处理策略**：
- **提示用户**：明确告知用户哪些依赖不满足
- **提供建议**：建议用户先执行依赖节点或执行完整工作流
- **自动修复**：如果可能，自动从更早版本获取数据（需谨慎使用）

## 9. 错误处理与恢复

### 9.1 错误分类

**节点级错误**：
- 节点执行超时
- 节点执行异常
- 节点输入数据验证失败
- 节点配置错误

**系统级错误**：
- 内存数据存储异常
- 版本管理异常
- 状态管理异常
- 依赖检查异常

### 9.2 错误处理策略

**节点执行失败**：
1. 捕获异常并记录详细错误信息
2. 更新节点状态为FAILED
3. 存储错误信息到节点执行数据
4. 根据节点重要性决定是否终止整个执行
5. 通知前端节点执行失败

**系统级错误**：
1. 记录错误日志
2. 尝试恢复系统状态
3. 如果无法恢复，终止执行会话
4. 通知管理员

### 9.3 执行恢复

**恢复场景**：
- 系统异常重启后恢复执行
- 网络中断后恢复执行
- 用户手动恢复执行

**恢复策略**：
1. 从数据库加载最近的执行会话状态
2. 重建内存数据存储（恢复最近N个版本）
3. 检查执行会话状态：
   - 如果状态为RUNNING，尝试恢复执行
   - 如果状态为FAILED，允许用户重新执行
4. 对于中断的节点，根据情况决定重新执行或跳过

## 10. 性能优化考虑

### 10.1 内存优化

**数据压缩**：
- 对于大型数据对象，考虑压缩存储
- 使用引用计数管理数据生命周期
- 及时清理不再使用的数据

**数据结构优化**：
- 使用高效的数据结构（如哈希表）实现快速查找
- 避免不必要的数据复制
- 使用对象池减少内存分配

### 10.2 执行优化

**并行执行**：
- 对于没有依赖关系的节点，考虑并行执行
- 使用线程池或进程池管理并发执行
- 控制并发数量避免资源耗尽

**缓存策略**：

## 14. 风险评估与应对

### 14.1 技术风险

**风险1：内存数据丢失**
- **影响**：系统重启导致内存数据丢失
- **应对**：实现定期持久化机制，系统重启时恢复数据

**风险2：并发执行冲突**
- **影响**：多个执行会话同时修改同一版本数据导致冲突
- **应对**：实现版本锁定机制，同一版本同时只能有一个执行会话写入

**风险3：内存溢出**
- **影响**：大量数据版本导致内存不足
- **应对**：实现版本数量限制和自动清理机制

### 14.2 业务风险

**风险1：数据版本混乱**
- **影响**：用户无法区分不同版本的数据
- **应对**：提供清晰的版本管理界面和版本标识

**风险2：依赖关系复杂**
- **影响**：部分执行时依赖关系处理错误
- **应对**：实现完善的依赖检查和错误提示机制

**风险3：执行性能下降**
- **影响**：内存数据存储导致查询性能下降
- **应对**：优化数据结构和查询算法，使用缓存机制

## 15. 总结

本设计方案提供了一个完整的工作流执行系统升级方案，支持三种执行模式，建立了完善的数据版本管理和状态管理机制。通过内存数据存储实现快速的数据访问，通过版本管理确保数据的完整性和可追溯性。

关键设计要点：
1. **数据版本管理**：区分完整执行和部分执行的数据版本策略
2. **状态管理**：三层状态管理确保系统状态清晰可追踪
3. **内存数据存储**：高效的数据存储和查询机制
4. **依赖处理**：完善的依赖检查和错误处理机制
5. **用户体验**：直观的执行控制和状态可视化

该方案在保证系统稳定性和性能的同时，提供了灵活的执行模式，满足不同场景下的工作流执行需求。
